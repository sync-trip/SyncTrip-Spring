## ✅ 현재 구현 상황

### 1. 검색 알고리즘 (Line 135)
✅ 문서: "1km 2단계 폭포수"
✅ 현재: **1km 3단계 폭포수로 확장**

  Stage 0: 0~1km (1단계)
  Stage 1: 1~2km (2단계)  ← 문서에 없음, 우리가 추가
  Stage 2: 2~3km (3단계)

**개선점:** 
  - Step 1: 가까운 후보 우선 추천 (사용자 만족도 높음)
  - Step 2: 부족할 때만 한 단계 확장 (비용 효율)
  - Step 3: 정말 부족할 때만 3km까지 확장 (최후의 수단)
  → "점진적 탐색"으로 품질 + 효율 동시 달성 ⭐

### 2. 최대 후보 개수 (Line 136)
❌ 문서: "7개"
✅ 현재: **3개로 제한**

  - 상위 3개 + Stage별 메타 추가로 충분 ⭐

## ⭐ 우리가 추가한 기능 (문서에 없음)
────────────────────────────────────────────────────────────────

### 1. 3단계 반경 확장 (1km → 2km → 3km)
✅ 우리 추가: **문서는 "2단계"지만 3km까지 확장**

**전략:**
  - Stage 0 (1km): "근처 대체 장소" → 첫 선택지
  - Stage 1 (2km): "2km까지 확장" → 부족할 때
  - Stage 2 (3km): "3km까지 확장" → 마지막 수단

**효과:**
  - 항상 추천을 줄 수 있음 (최대 3개)
  - 거리 조건은 동적이고 투명함 (사용자가 선택 가능)
  - 비용 효율 (외부 API 호출 없음)

### 2. 우선순위 점수 최소 임계값 (≥0.3)
✅ 우리 추가: **너무 낮은 점수 후보 제외**

  ```java
  if (alt.getPriorityScore() < PLAN_B_MIN_PRIORITY_SCORE) continue;
  // 0.3 미만 제외 → 투표 점수가 극히 낮은 장소는 추천 안 함
  ```

**왜 필요:**
  - altPool이 모든 후보를 포함 (임계값 = CEIL(N/2)-2)
  - 그 중 정말 낮은 점수는 추천 가치 없음
  - 0.3은 보수적 기준 (60% 이상 회원의 동의 미달)

### 3. 단계별 메타데이터 (fallbackLevel, searchRadiusKmUsed)
✅ 우리 추가: **프론트 표시용 정보**

  ```json
  {
    "placeId": 1001,
    "searchRadiusKmUsed": 1.0,      // 이 단계의 반경
    "fallbackLevel": 0,              // 0=1km, 1=2km, 2=3km
    "distanceKmToTarget": 0.8,
    "recommendScore": 0.82
  }
  ```

**용도:**
  - fallbackLevel=0: "가까운 대체 장소 추천"
  - fallbackLevel=1: "근처에 부족해 2km 범위로 확장했어요"
  - fallbackLevel=2: "추천이 부족해 3km까지 확장했어요"
  → 투명한 UX

### 4. 디버그 API (GET /debug/plan-b)
✅ 우리 추가: **개발 시 로직 검증용**

  ```
  curl "http://localhost:8080/debug/plan-b?userId=1&bandId=10&targetPlaceId=100"
  
  응답:
  {
    "recommendationCount": 3,
    "fallbackStageCounts": {
      "0": 2,    // 1km 단계에서 2개
      "1": 1     // 2km 단계에서 1개
    },
    "recommendations": [...]
  }
  ```

**효과:**
  - 각 단계에서 몇 개씩 뽑혔는지 시각화
  - fallbackLevel 분포 확인
  - 반경 확장 로직 동작 검증
